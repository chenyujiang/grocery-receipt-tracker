# Grocery Receipt Tracking & Price Monitoring App — Requirements Planning Map

## Destination

Produce a complete product requirements document (spec): a family-shared "photograph grocery receipts to track spending and unit prices" web app that supports bilingual (Chinese/English) data content.

The document must clearly define the feature scope, core data structures, the AI recognition (multimodal LLM OCR) approach, product matching and categorization logic, monthly price-change comparison, consumption-rate analysis, the bilingual translation mechanism, and the additional features: price-spike alerts, low-stock alerts, hidden price-hike detection, multi-store price comparison, and data export/monthly reports.

Once the document is complete, it will be handed off to the development phase for implementation (implementation itself is out of scope for this planning effort).

## Notes

- Domain: personal/family expense tracking + product price monitoring.
- Decided: receipt text recognition uses a multimodal LLM (e.g. the Claude / GPT-4V family), not a dedicated OCR API or a self-trained model.
- Decided: built for family sharing (multiple people recording together), not a single-user scenario; the project is also planned to open up to friends after completion, so it needs a proper account/registration system that supports multiple independent users/groups, not just a single family's invite-code model.
- Decided: build the web app first; a native/cross-platform app is deferred to a future roadmap and is not part of this round.
- Decided: the tech stack direction is React.js + TypeScript + Node.js, deployed on Vercel (frontend/API) + Supabase (database/auth), with GitHub for version control.
- Decided: the user is based in New Zealand, so receipts are originally in English (from supermarkets like Countdown, New World, PAK'nSAVE), not Chinese.
- Decided: the product must support Chinese/English bilingual content — dynamic data (product names, store names, category labels) is stored bilingually, with `_en` being the OCR-recognized English source text and `_zh` the Chinese translation produced by that same multimodal-LLM call; fixed UI chrome (menus, buttons) is English-only, with no language switch.
- Communication is in Chinese throughout; the map and ticket documents are bilingual with sentence-by-sentence pairing (Chinese above, English below), mirroring the product's own bilingual requirement.
- Each ticket is preferentially resolved via `/grilling` (paired with `/domain-modeling` to capture terminology and data structures); `/research` may be borrowed temporarily when comparing external technology options.

## Decisions so far

- [Platform choice (01-platform-choice)](https://github.com/chenyujiang/grocery-receipt-tracker/issues/2) — Build the web app first, native app deferred to a future roadmap; tech stack direction is React+TS+Node.js / Vercel+Supabase / GitHub.
- [Account & sharing model (02-family-sharing-model)](https://github.com/chenyujiang/grocery-receipt-tracker/issues/3) — Supabase Auth email login; one account per circle (default cap 10 members); owner/member roles, members can only edit/delete their own records; email invite links; duplicate detection by store+date+amount; buyer field = login email.
- [Receipt data schema (03-receipt-data-schema)](https://github.com/chenyujiang/grocery-receipt-tracker/issues/4) — Photo upload → AI draft → user reviews and confirms before it's saved; a Receipt/ReceiptItem/EditLog three-table structure, spec split into value+unit, promotions flagged with original price kept; original photos kept 12 months in Supabase Storage; upload uses a standard file input, covering both camera capture and gallery selection.
- [Category taxonomy (04-category-taxonomy)](https://github.com/chenyujiang/grocery-receipt-tracker/issues/5) — A two-level, system-fixed category list (9 top-level categories such as food/household); AI must pick from the preset list, never invent categories; user corrections are remembered and auto-applied to the same product name.
- [Bilingual content strategy (09-bilingual-content-strategy)](https://github.com/chenyujiang/grocery-receipt-tracker/issues/10) — Only dynamic data content is bilingual (product names/store names/categories), stored as `_zh`/`_en` columns, with `_en` as the OCR English source text and `_zh` as the translation produced by that same LLM call; this required updating the field design of tickets 03 and 04. **Amended post-launch**: fixed UI chrome is fully translated too (not English-only), via a hand-written string dictionary, driven by the same toggle as the data content.
- [Product matching strategy (05-product-matching-strategy)](https://github.com/chenyujiang/grocery-receipt-tracker/issues/6) — AI suggests a match candidate, the user confirms/changes it in the existing preview flow; barcodes are not handled; spec changes still count as the same product, with spec as a per-purchase-record attribute; adds a Product table (`product_id`) that tickets 06/07 will group by, and category memory's key also migrates to `product_id`.
- [Price-change calculation (06-price-change-calculation)](https://github.com/chenyujiang/grocery-receipt-tracker/issues/7) — Compares against the last purchase price, excluding promotional rows; weight/volume units are normalized to a per-100g/100ml basis before comparing, count-based units are not normalized; the page shows a price-change leaderboard, a per-product trend chart, and red/green color coding for increases/decreases.
- [Consumption-rate calculation (07-consumption-rate-calculation)](https://github.com/chenyujiang/grocery-receipt-tracker/issues/8) — A sliding window of the last 5 purchases (total quantity ÷ total days) gives the average daily consumption rate; fewer than 3 purchases means no estimate is shown; a reminder triggers when estimated days remaining drops below 5; fully automatic, with no manual "used up / not used up" marking required.
- [Tech stack & storage (08-tech-stack-storage)](https://github.com/chenyujiang/grocery-receipt-tracker/issues/9) — OCR + translation uses **Claude Haiku 4.5** via the Anthropic Claude API; calls must be proxied through a Vercel Serverless Function backend, keeping the API key out of the frontend; receipt images live in a private Supabase Storage bucket, accessed via signed URLs. **Superseded**: the global hard $1 cap described here is replaced by ticket 15's per-user credit model — see below.
- [Price-spike alert rules (10-price-spike-alert-rules)](https://github.com/chenyujiang/grocery-receipt-tracker/issues/11) — A fixed 15% increase triggers an alert; checked immediately after each receipt is confirmed; visible to all circle members; an in-app notification list plus a single email batched per receipt; per-product muting not built for now.
- [Low-stock alert rules (11-low-stock-alert-rules)](https://github.com/chenyujiang/grocery-receipt-tracker/issues/12) — A daily scheduled job scans all products; a `low_stock_alert_active` flag ensures only one reminder per episode until it recovers above the threshold; reuses ticket 10's in-app list and email template, also visible to all members.
- [Multi-store price comparison (13-multi-store-price-comparison)](https://github.com/chenyujiang/grocery-receipt-tracker/issues/14) — Confirmed in scope; reuses ticket 06's promotion-filtering and unit-conversion rules, comparing each store's latest normal price; shown as a module on the per-product page next to the price trend chart, not a standalone page; no comparison is shown if the product has only been bought at one store.
- [UI structure & language toggle (14-ui-structure-and-language-toggle)](https://github.com/chenyujiang/grocery-receipt-tracker/issues/15) — Page list (home/photo upload/receipt list/product detail/monthly report/notification center/circle settings); bottom tab-bar navigation plus a floating photo-upload button; bilingual content is shown via a language toggle displaying one language at a time; pixel-level visual design is left for implementation/prototyping. **Amended post-launch**: upload became a normal fifth tab (five even items), Notifications moved to a pinned top-right icon, the receipt list gained per-row delete and a read-only detail page for confirmed receipts, and every date-range picker unified on a year-then-month popover (month-level, not day-precise).
- [Data export & report format (12-data-export-report-format)](https://github.com/chenyujiang/grocery-receipt-tracker/issues/13) — CSV line-by-line export, whole-circle data with a selectable time range; a standalone monthly report page rolls up total spend vs. last month, category breakdown, the price-change leaderboard (reusing ticket 06), alert counts, and per-uploader spending, with the export button living on that same page. **Amended post-launch**: the exportable range is a from-month/to-month picker, not an arbitrary custom start/end date.
- [Admin dashboard & per-user AI credits (15-admin-dashboard-and-per-user-credits)](https://github.com/chenyujiang/grocery-receipt-tracker/issues/16) — New global-admin identity (separate from per-circle owner), reached via a hidden/unguessable route (real auth check + 404-on-deny, obscurity as a bonus layer, not a substitute); replaces ticket 08's global spend cap with a per-user dollar cap that the admin "grants" as a reset-to-fresh-allowance (default $1, or custom); disable/enable via Supabase Auth's own ban mechanism; brand-new users get a hard 1-free-successful-call trial (not a dollar amount) before needing an admin grant; blocked users get a `mailto:` link to the admin, no backend email sending; admin lands on the dashboard once post-login, with a manual switch back to the normal app; existing users are grandfathered straight into the dollar-cap model, skipping the free-trial gate. UI direction settled via `/prototype` (a needs-attention queue + circle-grouped roster, rendered as cards). Schema drafted, then **implemented and shipped**: `global_admins` + `user_ai_access` tables/RLS applied to the live project, `api/_lib/userAiAccess.ts` replacing `spendLimit.ts` (deleted), `api/admin/*` routes, `src/pages/AdminDashboard.tsx`, `RequireGlobalAdmin` route guard, and the post-login redirect — all TDD, all green (48 test files / 199 tests). CLAUDE.md updated to describe the new model. Committed and pushed to `origin/main`. **Amended post-launch**: the admin identity ended up being the project owner's existing family account rather than a separate dedicated one; Circle Settings also got a persistent "Go to admin dashboard" link (the one-time post-login redirect alone wasn't enough for an already-live session). Also surfaced a **known open bug, not yet root-caused**: new-account signup intermittently fails to auto-create its circle/profile (RLS rejects the insert as if unauthenticated, despite Supabase Auth itself succeeding) — see the ticket for the request-log evidence; needs a real fix before opening signup beyond the single grandfathered account.

- [Edit a confirmed receipt (16-edit-a-confirmed-receipt)](https://github.com/chenyujiang/grocery-receipt-tracker/issues/17) — Inline "Edit" toggle directly on `ReceiptDetail.tsx` (not a separate route), uploader-only (matches the existing delete permission, no RLS change needed since RLS never had a status check to begin with). Editable: name/quantity/unit price/promotion (already editable pre-confirm), plus purchase date (via the existing month-only `MonthPickerField`, day-of-month preserved rather than reset to the 1st) and the weight/volume spec value+unit — but only for items that already have a unit set, and only as a fixed g/kg/ml/L dropdown, not free text, since that's the only set `units.ts` actually normalizes. Reuses `diffReceiptItemFields`/`edit_logs` as-is. Price-spike alerts are deliberately not re-triggered on edit — old alerts stand as-is, right or wrong. **Implemented and shipped**: `editConfirmedReceipt` added to `src/lib/receipts.ts`, `ReceiptDetail.tsx` got the edit toggle — all TDD, all green (210 tests). Not yet manually verified against the real deployed app (no test login available this session).

- [Unify the receipt item editor (17-unify-receipt-item-editor)](https://github.com/chenyujiang/grocery-receipt-tracker/issues/18) — One shared controlled `ReceiptItemFields` component for Review and Detail's edit mode, with `toItemUpdate()` in `src/lib/receipts.ts` as the single place the Section 5.2 category strip happens (`ConfirmReceiptItemUpdate` becomes `Omit<DraftItem, "category">`). Rejected widening `confirmReceipt` to accept `DraftItem[]`: that buries the 5.2 rule behind an API that silently discards a field it accepts. The field sets converge upward, so the weight/volume spec becomes editable in Review too — a deliberate behavior change, since an OCR'd spec is strictly safer to fix before confirming than after. Category stays out of the component (it isn't a ReceiptItem field), and the seam is the component rather than a `useDraftItems` hook. **Known defect left in place**: editing quantity/unit price doesn't recompute `subtotal` — it predates this change and turns on unsettled promotion-price semantics.
- [Authenticate the cron route (19-authenticate-the-cron-route)](https://github.com/chenyujiang/grocery-receipt-tracker/issues/20) — The scheduled low-stock sweep ran unauthenticated. Now non-`GET` returns 405; `Authorization: Bearer $CRON_SECRET` is compared against the env var, with missing/malformed/mismatched returning 401; and an **unset** `CRON_SECRET` fails closed rather than skipping the check. Each rejection test also asserts `supabaseAdmin.from` was never called — a route that 401s *after* sweeping every Circle would still have done the damage. **Still needs a human**: `CRON_SECRET` must be added to the Vercel project env, or the scheduled run fails closed and no low-stock alerts are generated.
- [Cron bypassed fetchPurchaseHistories (20-cron-bypasses-fetch-purchase-histories)](https://github.com/chenyujiang/grocery-receipt-tracker/issues/21) — Not a bug that was written but one that got **un-fixed**: the batched integration already existed and was reverted mid-flight, leaving `src/lib/purchaseHistory.ts` untracked with nothing importing it. Fixed by `61176b0`, which routed the cron handler plus `receipts.ts`/`monthlyReport.ts`/`productDetail.ts` through `fetchPurchaseHistories` and collapsed a `ProductPriceHistory` type that had been declared twice with different bodies. The lesson is about the filing, not the code: an untracked module that nothing imports means ask before filing.
- [Reject invalid grant amounts (21-reject-invalid-grant-amounts)](https://github.com/chenyujiang/grocery-receipt-tracker/issues/22) — **Specified, not yet implemented** (`ready-for-agent`). `grant-credit.ts` silently downgrades an unusable `capUsd` (`"5"` as a string, `0`, `-5`, `NaN`, `Infinity`) to the default $1 and still returns 200, so the admin believes they granted what they typed. This bites harder than a typical validation gap because a grant is always a reset, never a top-up (ticket 15 decision 4): a mistyped grant zeroes the user's spend and caps them at $1, and nothing auto-corrects. Decision: an **absent** `capUsd` keeps meaning "reset to the default"; **present but not a finite number > 0** returns 400 with no grant attempted.
